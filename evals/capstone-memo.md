Before I begin my review of the API integration for the research agent, I would like to address the process that led me to module 9 and the lessons I learned throughout. Until module 7, like most interns, I was smooth sailing and finished quickly. Once I arrived at module 7, I lost focus of the workflow and planning that had been reiterated numerous times in the coursework leading up to and including module 7: I didn’t break up tasks. By following the instructions, which were very helpful in and of themselves, and relying on the situational blindness of Claude, I ended up putting the fate of the final product in anyone’s hands but my own.   
Going forward, I will break up tasks into pieces that are not just comprehensible for the AI, but also for myself. Whether this means starting a new session or chat for a new [SKILL.md](http://SKILL.md) file or contract, or breaking up python architecture into intuitive segments rather than a single pipeline, I need to start thinking and planning with more dexterity– able to trust AI but verify, pivot but not lose course.   
I found the API to be the intriguing part of the course and project because of its similarity to the way that a student would study for a standardized test. When I studied for the SAT, the two best strategies to succeed were volume(larger and more diverse evaluation sets) and refinement of the thinking process by going over errors(prompt rewriting). For API this combo improved my API accuracy from 50%(Claude prompts) to over 70%(refined prompts).  
For live implementation, the API would be worthy of replacing the skill because of its scalability and malleability. Instead of entrusting the results of a skill to two examples in a [skill.md](http://skill.md) or contract file, as more data-rich cases emerged–for example if this agent was for MF PE and not MM, –the evaluation set can include more complex analysis and claims exactly because there is more volume. More simply, if the agent were live, and applied to any MM firm, the ability to reason independently of any one set of information or circumstances would be worth dividends.   
While one could argue the diminishing returns of a larger evaluation set and cite the human time required to make, grade, reprompt, etc, I believe that before diminishing returns set in(which they would), the diversity of claims/circumstances/reasoning scenarios would already produce a great product that is reliable. In essence, once you get to a certain point, the APi confidence-scorer should be ready for anything. And given the scope of what its scoring–claims on portcos, firm strategy, firm profiles, financial approximations–there are only so many different curveballs that could be thrown at it.   
	For production, opus would be more expensive than a sonnet confidence-scorer pass. Interestingly though, I found the API to be faster than the skill pass-through. I believe that this is due to the simplification of the reasoning process and opus having better reasoning. Instead of a rubric, contract, and [skill.md](http://skill.md) file, the API has a prompt and a question to answer. This makes it more reliable and less latent. I would also like to note that if the claims are fed to the API in the same way that they are the confidence scorer(single batch), the API could easily be dispatched to groups of claims and run in parallel, ensuring that it surpasses the pass-through in efficiency.
